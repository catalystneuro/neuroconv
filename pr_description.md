# Add an MNE-backed base interface for continuous biopotential recordings

NeuroConv's model is to wrap a mature domain reader rather than hand-parse a format, which is why recordings go through SpikeInterface and imaging through roiextractors. For the EEG/MEG family that neither covers (EEGLAB, BrainVision, EGI, FIF), the mature reader is MNE-Python, so this adds `BaseMNEContinuousDataInterface`: a subclass builds an `mne.io.BaseRaw` in `_read_raw()` and the base does the rest. The shape differs from the SpikeInterface base in one way worth knowing. SpikeInterface has one extractor class per format, which forces a subclass per format; MNE has a single `Raw` type produced by per-format functions, so the base could in principle serve every format on its own and the subclass split is a consistency choice rather than a structural necessity.

An MNE `Raw` mixes channel kinds in one object, so the base partitions them: the electrode kinds (`eeg`, `seeg`, `ecog`, `dbs`) become one `ElectricalSeries`, and everything else becomes a `TimeSeries` of its own per channel type, carrying that type's unit. Nothing is dropped and nothing raises, which matters because the alternatives all lose data the file recorded. The routing keys off channel type rather than unit, since MNE labels trigger lines as volts exactly as it labels EEG channels, so a unit test would quietly sweep them into the neural series. I put `eog`, `ecg` and `emg` in `TimeSeries` even though they are genuine electrode voltages, on the grounds that the electrodes table describes electrodes on neural tissue and an ECG lead is not that. I would treat all of this as interim: biopotential signals really want their own extension, and when one exists the question of what belongs in an `ElectricalSeries` gets answered there rather than here.

Electrode coordinates are left out entirely, not even `rel_x/y/z`, and that is the same interim judgment. MNE's head frame does not match the brain-localized convention the electrodes table documents for `x/y/z`, NWB pins no unit on either set of columns, and the fiducials that would let you reconstruct the frame or round-trip a montage back to MNE have nowhere to go at all. Writing nothing is valid, since only `location` and `group` are required, and it commits to no representation, so no file written today is stuck in something we migrate away from later. The electrodes table itself is still written because every `ElectricalSeries` references its rows.

Data streams through `MNERawDataChunkIterator` rather than `raw.get_data()`, so a `Raw` opened with `preload=False` is never materialized. That matters more than it might sound: MNE applies calibration on read and always hands back float64 whatever the file stores, so this is inherently the `physical_units` representation and the in-memory copy would be eight bytes per sample. A preloaded `Raw`, which some formats force when the data sits inline in the container, serves the same call from memory, so there is one code path and no fallback. The mock builds a synthetic `RawArray`, which is preloaded by construction and therefore cannot demonstrate any of this, so the laziness tests drive a real `.fif` from disk instead.
